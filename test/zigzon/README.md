# zigzon — conformance corpus from the Zig reference implementation

**Nothing in this directory except `tools/` and this file is committed.**
`cases.json` and `vendor/` are generated by
[`scripts/fetch-zigzon.sh`](../../scripts/fetch-zigzon.sh) and are
`.gitignore`d. Do not commit them — vendoring a third-party corpus is a hard
project rule, and the upstream material here is Zig's, not ours.

```bash
bash scripts/fetch-zigzon.sh     # idempotent; ~1 min cold, seconds warm
```

## Why the corpus is generated rather than downloaded

ZON has **no standalone third-party conformance suite**. There is no
`zon-test`, no `spec.json`, no committee fixture set — nothing equivalent to
`BurntSushi/toml-test` or the W3C XML suite. The only authority on what ZON
means is the Zig reference implementation.

So the corpus is assembled mechanically from a pinned Zig release, and — this
is the important part — **adjudicated by that same pinned release**. Neither
the document list nor the expected values come from this repo. A corpus graded
by the parser under test would measure nothing at all.

## The pins

| What | Value |
|---|---|
| Upstream repo | `https://codeberg.org/ziglang/zig` (canonical since the 0.16 dev migration off GitHub) |
| Tag / commit | `0.16.0` = `24fdd5b7a4c1c8b5deb5b56756b9dbc8e08c86a8` |
| Corpus artifact | `zig-0.16.0.tar.xz`, SHA-256 `43186959edc87d5c7a1be7b7d2a25efffd22ce5807c7af99067f86f99641bfdf` |
| Oracle toolchain | prebuilt zig `0.16.0`, SHA-256 pinned per platform in the fetch script |

The fetch is pinned by **content hash**, not by a branch or a git ref: a
SHA-256 over the exact bytes is a stronger guarantee than a tag, and it
survives the upstream repository moving hosts (which it just did). A hash
mismatch is a hard failure — the script will not "work around" it.

The oracle toolchain is the **same 0.16.0 release** as the corpus, so the
stdlib doing the adjudicating is exactly the stdlib the corpus ships with. The
script refuses to run against any other zig version.

## Where the documents come from

| Upstream path | What |
|---|---|
| `test/behavior/zon/*.zon` | official ZON behaviour documents |
| `test/cases/compile_errors/zon/*.zon` | official ZON **must-fail** documents |
| `build.zig.zon`, `lib/init/build.zig.zon`, `src/codegen/**/*.zon` | real-world manifests |
| `lib/std/zon/parse.zig` | ZON source literals inside `test` blocks |

`tools/extract.py` collects them and deduplicates on source text (the same
document appears in several places upstream; counting it twice would inflate
the denominator). It deliberately does **not** decide validity.

## How a verdict is reached

`tools/oracle.zig` runs, per document:

1. `std.zig.Ast.parse(src, .zon)` — syntax.
2. `std.zig.ZonGen.generate(...)` — lowering to an untyped value tree.

`ZonGen` is the right comparison layer. It produces an **untyped** tree, which
is exactly what `@tabnas/zon` produces. The layer above it, `std.zon.parse`,
additionally type-checks against a Zig type; those failures are *type* errors,
not ZON errors, and counting them here would overstate the failure rate.

Either stage reporting an error ⇒ `valid: false`. Otherwise `valid: true` plus
the canonical value.

### Canonical value encoding

JSON cannot carry everything a ZON value can, so the oracle spells the gaps:

| ZON | JSON in `cases.json` |
|---|---|
| `inf` / `-inf` / `nan` | `"@inf"` / `"@-inf"` / `"@nan"` |
| `-0.0` | `-0.0` (the sign is preserved deliberately — see below) |
| integer beyond f64 | `{"$big":"<decimal>"}` |
| enum literal `.foo` | `{"$enum":"foo"}` |
| char literal `'x'` | the codepoint, as a number |
| `.{}` | `[]` |

Both runners canonicalise their **actual** value the same way before
comparing, so a parser that gets `inf` or `-0.0` right can pass. That is
alignment of representation, not leniency — no input is ever excused.

> The signed-zero case is worth calling out: an earlier version of the oracle
> rendered `-0.0` as `0`, which made TypeScript (whose `deepStrictEqual` uses
> `Object.is`) fail a case it actually handled correctly, while Go passed it.
> The instrument was wrong, not the parsers. Fixed in `wf64`.

## What the suites assert

| Runner | |
|---|---|
| TypeScript | [`ts/test/zigzon.test.ts`](../../ts/test/zigzon.test.ts) |
| Go | [`go/zigzon_test.go`](../../go/zigzon_test.go) |

Both run under the normal `npm test` / `go test ./...`, over the same corpus
with the same options, and both cover **both halves**:

- **valid** → must parse **and produce the reference value**. Asserting only
  "it didn't throw" is the mistake that let a wrong-value bug hide in the json5
  plugin; it is not acceptable here.
- **invalid** → must be **rejected** with an error.

Options used: `{ enumTag: '$enum', charAsNumber: true }`. These put the
plugin's output in the same shape as the oracle's encoding so values compare
directly — `enumTag` in particular is what distinguishes the enum literal
`.foo` from the string `"foo"`, which the default flat encoding cannot do.

## This suite must never skip

If `cases.json` is absent the suites **fail** with instructions. They do not
skip. A conformance test that quietly does not run is worse than no test,
because the green tick is a lie — and that is precisely how these suites were
found to be reporting success while never executing.

`ts/package.json` has a `pretest` hook that runs the fetch, and
[`.github/workflows/conformance.yml`](../../.github/workflows/conformance.yml)
runs it as an explicit step before the tests.

## These are measuring instruments, not gates

They are **RED on purpose**. Do not shrink the corpus, add a skip list, narrow
the option set, or loosen the value comparison to improve a number. A
conformance figure that cannot fail is worth nothing. Fix the grammar, or
leave the case red with a written reason.
